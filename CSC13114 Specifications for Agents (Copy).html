A user story is not a specification

  • A story says who wants what, and why — it is an intention
  • A spec says what the system does, including when things go wrong
  • "As a customer I want to split the bill so we can pay separately" says nothing

about partial payments, rounding, or two people paying at the same second

  • Stories stay. They are the input to the spec, not a replacement for it

The five places every spec is thin

  1. Empty and first-run states — no items, no orders, a brand-new table
  2. Partial failure — the payment succeeded, the update did not
  3. Permissions — who may do this, to whose data
  4. Concurrency and duplicates — two people tap Pay in the same second
  5. Limits — page size, upload size, rate; and what happens at the limit

Whatever you leave out, the assistant decides for you — confidently.

The shape of a feature spec

# Split the bill
Status: draft · Owner: <name> · Feature of: smart-restaurant

## Goal          one sentence
## Out of scope  what this deliberately does NOT do
## Flow          numbered steps, happy path only
## Contract      endpoints, payloads, status codes
## Data          tables touched, fields added, invariants
## Errors        condition → what the user sees → what the system does
## Acceptance    AC1..ACn, each one runnable
## Constraints   no new dependencies · works on the current schema

Acceptance criteria that can fail

✗ AC1: splitting the bill works correctly

✓ AC1: a 405000đ order split 3 ways produces three shares of 135000đ;
       the sum of the shares always equals the order total
✓ AC2: if one share fails to pay, the order stays open and the other two
       shares stay paid — nothing is refunded automatically
✓ AC3: two simultaneous pay requests for one share produce one payment;
       the second returns 409 with the existing payment id
  • If you cannot imagine the test, it is a wish, not a criterion

The contract, written down

POST /api/tables/:id/bill/split
{ "mode": "equal", "ways": 3, "idempotencyKey": "uuid" }

201 { "shares": [ { "id": 1, "amount": 135000, "status": "unpaid" } ] }
409 { "error": "split_exists", "splitId": 42 }
422 { "error": "order_empty" }
  • Status codes are part of the contract — "it returns an error" is not a contract
  • The idempotency key is your answer to line 4 of the previous list

Non-goals are the cheapest lines you will ever write

  • "This feature does not support splitting by item" — one line, saves a week
  • "Refunds are out of scope: a failed share is retried, never reversed"
  • "No new dependency. No schema change beyond bill_shares"
  • Every non-goal is an invention you have pre-empted
  • Students skip this section. Reviewers read it first

The spec is the test plan

test('AC1 — shares sum to the order total', ...)
test('AC2 — one failed share leaves the others paid', ...)
test('AC3 — duplicate pay request returns 409 with the same id', ...)
  • Acceptance criteria become test names, one for one
  • The assistant may write the tests; the criteria are still yours
  • A spec with no runnable criteria produces code nobody can verify — including you

IA#1 — write this spec · 3%

Split the bill at a table, in smart-restaurant — the system you already built.

  • A table has one open order with several items, priced, VAT included
  • The customers want to pay separately, each from their own phone
  • The kitchen is not affected; the order stays open until every share is paid
  • Same feature for everyone, so the specs can be compared

One page. Use the template from slide 8. Deadline on Classroom.

IA#1 — then we swap

  • Your spec goes to another team; you receive theirs, in the next lab
  • They implement it with an assistant. Your spec is their brief — nothing else
  • They may not ask you anything. Every question they would have asked, they write down
  • That question list comes back to you, and you revise the spec

Hand in three files: the spec, the question list you received, the revised spec.

What we expect to find

  • Rounding: 405000 / 3 is exact, 400000 / 3 is not — who pays the extra đồng?
  • Who may split the bill: anyone at the table, or whoever opened it?
  • A share is paid, then an item is added to the order. Now what?
  • Two people paying the same share in the same second
  • Discounts and VAT: split before, or after?

Every one of these is a sentence you could have written in advance.

GA#1 — proposal and planning · 4%

No specification in this one. The spec comes later, once the idea holds up.

  • The product: who it is for, and the one problem it solves
  • The LLM feature you intend to build — and why being wrong there costs something
  • Scope for the semester: what is in, and what you are deliberately leaving out
  • Plan: the six checkpoints, who does what, what is due when
  • Risks: the two things most likely to sink this, and what you will do about each
  • Technology choices, one line of justification each

Two pages, plus your repository link. Teams of up to 3, named on the submission.
